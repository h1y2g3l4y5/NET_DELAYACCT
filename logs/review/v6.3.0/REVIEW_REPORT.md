##### 问题 2.1.1 — trace ring buffer 溢出未检测

**现象**：[ci/qemu/run-tests.sh#L2080-2084](file:///home/lai/Code/NET_DELAYACCT/ci/qemu/run-tests.sh#L2080-L2084) 直接从 `$TRACEFS/trace` 提取 skb 指针，未检查 trace ring buffer 是否溢出。trace 文件头部有 `entries-in-buffer/entries-written: N/M` 行，当 `N < M` 时说明有事件丢失。

**为什么是问题**：如果 ring buffer 溢出，tx_start 或 tx_end 的 skb 集合会不完整。最坏情况下，tx_start 的某些 skb 指针丢失，导致原本配对的 skb 被误判为错配（假阳性），或 tx_end 的 skb 丢失导致错配被漏检（假阴性）。

**触发条件**：iperf3 -t 3 在 KVM 硬件加速下产生大量 trace 事件（数千行），若 trace ring buffer 默认 size（通常 1408KB per CPU）不足以容纳所有事件，溢出就会发生。KVM 下事件生成速率远高于 TCG，溢出风险更大。

**后果**：per-skb 配对验证结果不可信——PASS 可能是漏检，FAIL 可能是假阳性。当前 30% 阈值提供了一定容错，但无法区分"ACK 导致的合法错配"和"buffer 溢出导致的数据丢失"。

**修法**：在提取 skb 指针前，检查 trace 头部的 entries-in-buffer/entries-written 比率：
```bash
OVERFLOW=$(head -5 "$TRACEFS/trace" 2>/dev/null | grep 'entries-in-buffer' | sed 's/.*entries-written: \([0-9]*\)\/\([0-9]*\).*/\1 \2/' | awk '{if($1<$2) print "OVERFLOW:"$1"/"$2}')
if [ -n "$OVERFLOW" ]; then
    echo "    [warn] trace ring buffer overflow detected: $OVERFLOW (results may be unreliable)"
fi
```
或在测试开始前增大 buffer：`echo 4096 > "$TRACEFS/buffer_size_kb"`。

**为什么这么修**：检测溢出是最低成本方案（不改测试逻辑，只加诊断信息），让 Reviewer/Worker 在分析结果时能判断数据可信度。增大 buffer 是预防方案，但需确认 QEMU guest 内存够用。

### 2.2 设计合理性 (9/10)

#### 优点

1. **双断言设计（强+弱）优秀**：per-skb 子集检查是强断言（精确匹配），计数比是弱断言（粗筛）。两者都通过才 PASS，任一失败都 FAIL。这种设计既能发现"count 相等但 skb 错配"的隐蔽缺陷（v6.2.0 计数比无法发现），又保留了计数比的快速失败信号。

## 四、踩坑点评

### 坑1：kprobe 入口触发 vs 内部守卫早返回
- **Worker 处理**：✅ 优秀。准确识别了"kprobe 在函数入口触发，内部守卫早返回不影响捕获"这一机制，并据此设计了 ACK 容忍阈值。这是本版本最核心的技术洞察。
- **深层启示**：kprobe events 验证的是"函数被调用"而非"函数执行有效逻辑"。设计 kprobe 验证断言时，必须结合函数内部语义，不能仅依赖调用次数。

### 坑2：kprobe arg `:u64` 输出十进制
- **Worker 处理**：✅ 正确。awk 解析器兼容任意格式（`sub(/^skb=/,"",$i)`），不依赖具体进制。
- **深层启示**：kprobe arg 类型后缀（`:u64` vs `:x64`）决定输出格式。设计解析器时应先确认实际格式或兼容多种格式。

### 坑3：KVM/TCG ACK 占比差异导致阈值失败
- **Worker 处理**：✅ 优秀。CI 失败后准确诊断根因（KVM TCP 处理更快，ACK 占比 ~26% vs TCG ~8%），并将阈值从 10% 调整为 30%。修复后 CI 全绿。
- **深层启示**：再次证明"本地 TCG 通过 ≠ CI KVM 通过"。计数/阈值类断言必须以 KVM 数据为基准设计，因为 KVM 是生产环境的标准配置。这个教训已同步到 project_memory.md。

### 坑4：提取公共函数时变量作用域变化
- **Worker 处理**：✅ 正确。`yes` 变量在 burst 循环内重新声明，作用域限定在 if 块内。
- **深层启示**：提取公共函数时，需检查所有引用的外部变量是否应作为参数传入或在函数内重新声明。这是一个通用的重构注意事项。
