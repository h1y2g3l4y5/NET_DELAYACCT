**问题 2.1.1 — retrans 剔除无最小有效样本数防护**

- **现象**：[run-perf-tests.sh#L237-L243](file:///home/lai/Code/NET_DELAYACCT/ci/qemu/run-perf-tests.sh#L237-L243) 采样循环中 `latency_us > 100000` 即剔除，不限制剔除比例；`latencies` 为空时 percentiles 直接基于零样本计算。
- **为什么是问题**：100ms 阈值锚定 KVM 模式（正常 p999 10-20ms）。测试脚本的 TCG 回退路径（`-accel=tcg`，QEMU_TIMEOUT_KVM 超时后启用）下指令执行慢 30-50 倍，正常 connect 延迟可能整体 >100ms——此时**全部真实样本被当伪影剔除**。
- **触发条件**：CI 在 KVM 不可用或超时时回退 TCG 跑 perf（该路径在现有 workflow 中真实存在），且 runner 较慢。
- **后果**：`latencies` 为空 → 各 percentile 输出空/0 → 中位数失真 → K0/K2 同失真时 delta 可能显示 0% PASS，产出**假 PASS 报告**；retrans=100 虽可人工发现，但 verdict 机器判定不会拦截。
- **修法**：采样循环后加防护：
  ```sh
  if [ $retrans_cnt -ge $((NUM_SAMPLES / 2)) ]; then
      echo "PERF: tcp_latency_p50_run${run}=SKIP"   # 或输出 INVALID 标记
  fi
  ```
  剔除过半时该轮按 no-data 处理，走既有的 SKIP/INVALID 三态路径。
- **为什么这么修**：项目已有三态判定基建（v6.1.0 共识：INVALID 处理噪声），复用现有路径比发明新状态更一致；`>=50%` 与 CI exit 判定的 INVALID>50% 阻塞线对齐。

**问题 2.4.1 — 本轮工作未按流程记录 work 日志（事后补记）**

- **现象**：本轮 4 个 commit + ftrace 调查的工作日志为审查前补记（logs/work/2026-08-16/ 创建于 review 阶段），日志目录在 8/6 后出现 10 天空档。
- **为什么是问题**：Worker/Reviewer 协作流程约定工作日志由 Worker 在工作发生时记录，是 review 的输入而非 review 的产物。事后补记意味着「审查基于自述」——本轮因 diff 和 CI 记录完备而可交叉验证，但不能依赖每次都如此。
- **触发条件**：任何一轮「用户直接驱动、跳过 worker 流程」的快节奏修复（本轮即如此：用户在对话中直接下达修复指令）。
- **后果**：review 失去独立信源；若补记时有记忆偏差，review 无法发现；日志时间戳与实际工作时间的关联断裂。
- **修法**：快节奏会话中至少在批次收尾时（而非 review 时）落一份 TASK 日志；或在 project_memory 增加「对话驱动工作流需在批次结束时补日志」的提醒规则。
- **为什么这么修**：不要求逐任务实时记录（打断工作流），但批次边界（push 验证完成/结案）是自然的落盘点，成本最低。

## 四、踩坑点评

- **坑 1（本地内核 KASLR 死循环）**：处理得当——nokaslr 绕过 + 教训归档（本地复现须重做 defconfig）。暴露的深层问题：本地树与 CI 构建环境漂移无检测手段，建议未来在 ftrace 实验脚本中加 config diff 校验。
- **坑 2（用户终端 QEMU 三坑）**：通过 `-serial file:` 结构性解耦而非继续调参，是正确的「绕过优于纠缠」决策。归档价值高（CI 环境正常会掩盖此类问题）。
- **坑 3（initramfs shebang ENOENT）**：从 `error -2` 到 `/bin/bash` 绝对路径的定位干净利落。busybox 环境推荐 `#!/bin/sh` 的结论已入 memory。
- **坑 4（sysctl 未生效 → strace 定位 backlog=1）**：本轮最有价值的教训——「调系统参数前先确认工具实现」。Worker 从「调优失败」正确转向「黑盒工具实锤」，避免了继续在内核参数上浪费时间。
