## 三、问题展开详情

### 问题 2.1.1 — perf-test "exit 0" 标注未区分 warn 与 pass（低）

- **现象**：[TASK-55 §5.2 表格](file:///home/lai/Code/NET_DELAYACCT/logs/work/2026-08-06/TASK-55_test24-flakiness.md#L125) 及各文档多轮 verdict 表中，perf-test 标注为 `✅ exit 0 (167s)`，与 checkpatch/build 等 `✅ success` 并列。
- **为什么是问题**：perf-test 在 `--strict=warn` 模式下，FAIL → exit 0（告警）。即"exit 0"涵盖三种情况：全 PASS、有 FAIL 但未达 exit 2 阈值、有 INVALID 但 <50%。把"exit 0"与功能测试的"success"用相同 ✅ 并列，读者会误读为"性能全部达标"。
- **触发条件**：读者快速浏览 verdict 表时，将 perf-test `✅ exit 0` 理解为"无性能回归"。
- **后果**：低 — Worker 在备注里已写"perf-test FAIL→warn 设计生效"，但表格主列仍易误读；不影响功能，仅影响报告可读性。
- **修法**：perf-test 列标注改为 `✅ exit 0 (warn)` 或 `✅ exit 0 (signal)`，与功能测试 `✅ success` 区分语义。
- **为什么这么修**：与 v6.5.0 "signal not gate" 设计哲学一致 — perf-test 是趋势信号非门禁，标注应反映"未阻断"而非"全通过"。

### 问题 2.3.1 — #144 数据点遗漏，修复前统计偏紧（中）

- **现象**：[TASK-55 §5.2 对照表](file:///home/lai/Code/NET_DELAYACCT/logs/work/2026-08-06/TASK-55_test24-flakiness.md#L131-L136) 与 [TASK-48 补遗表](file:///home/lai/Code/NET_DELAYACCT/logs/work/2026-08-06/TASK-48_multi-round-perf-data.md#L126-L134) 的"修复前"轮次为 #137/#139/#140/#141/#142/#143（6 轮），但实际还有 **#144 (055c89e)** — Reviewer 独立复核确认 #144 也是 6/6 success，且其 run-tests.sh 仍为 200% 阈值（修复前代码）。#144 在 TASK-48 补遗初版曾以 `in_progress` 出现，最终表中被移除且未记录结论。
- **为什么是问题**：#144 是修复前 success 数据点，对理解 flakiness 间歇性至关重要。修复前实际序列为 7 轮（5 ✅ + 2 ❌，失败率 28.6%），而非 Worker 呈现的"4 轮 2 失败"（50%）。遗漏 #144 使 flakiness 看起来比实际更严重，间接放大了"250% 阈值必要性"的论证。
- **触发条件**：Reviewer 独立查询 #144 (055c89e) check-runs 时发现 6/6 success；进一步查 055c89e 的 run-tests.sh 确认仍是 200% 阈值。
- **后果**：① 数据完整性受损 — 多轮统计漏 1 轮 success；② 论证偏差 — "4 轮 2 失败"比"7 轮 2 失败"更能支持放宽阈值的决策，遗漏使决策依据偏紧；③ 后续若有人复盘"为何选 250% 而非更保守值"，缺失的 #144 会让人误判 flakiness 频率。
- **修法**：在 TASK-48 补遗表和 TASK-55 对照表中补回 #144 (055c89e, 修复前, 6/6 success, QEMU test ✅) 一行；更新"修复前 N 轮 X 失败"统计为 7 轮 2 失败。
- **为什么这么修**：数据完整性是阈值决策的根基。v6.5.0 的核心方法论是"多轮数据驱动校准"，遗漏数据点违背该方法论。补回 #144 不改变"250% 阈值合理"的结论（203-209% 仍超 200%），但让论证更诚实。

### 问题 2.4.1 — 单轮验证结论措辞过强（中）

- **现象**：多处文档用绝对措辞描述单轮验证结果：
  - [TASK-55 L127](file:///home/lai/Code/NET_DELAYACCT/logs/work/2026-08-06/TASK-55_test24-flakiness.md#L127)：`Test 24 flakiness 修复**验证通过**`
  - [TASK-55 L138](file:///home/lai/Code/NET_DELAYACCT/logs/work/2026-08-06/TASK-55_test24-flakiness.md#L138)：`250% 阈值覆盖了共享 runner 调度噪声（203-209% 区间）`
  - [FINAL_REPORT L223](file:///home/lai/Code/NET_DELAYACCT/logs/summary/v6.5.0_FINAL_REPORT.md#L223)：`确认 250% 阈值覆盖了 203-209% 噪声区间`
  - [PERFORMANCE.md L300](file:///home/lai/Code/NET_DELAYACCT/docs/PERFORMANCE.md#L300)：`6/6 全绿，Test 24 不再 flaky`
- **为什么是问题**：Test 24 flakiness 的本质是**间歇性**的 — 修复前 #143 和 #144 都是 success（噪声退去），#141/#142 才失败。单轮 #145 success 无法区分两种解释：① 250% 阈值生效；② 恰好本轮噪声低（如 #143/#144）。"验证通过""确认覆盖""不再 flaky"等措辞把单轮观察上升为确定结论，与 flakiness 的统计本质不符。Worker 自己在待办里写"长期监控：观察 10+ 轮 CI run 确认 250% 阈值稳定"，说明 Worker 知道单轮不足，但正文措辞比待办更强。
- **触发条件**：共享 runner 调度噪声低的轮次，200% 和 250% 阈值都会 PASS（如 #143/#144）。单轮 #145 恰好可能落在低噪声窗口。
- **后果**：① 给读者"flakiness 已解决"的过强信心；② 若后续轮次 ratio 再超 250%（极端噪声），与"确认覆盖/不再 flaky"措辞矛盾，损害文档可信度；③ 与 v6.5.0 "signal not gate" 哲学相悖 — 该哲学承认单次结果不可靠，但措辞却把单次结果当确定结论。
- **修法**：将绝对措辞改为概率性/阶段性措辞：
  - "验证通过" → "首轮验证通过（待长期监控确认）"
  - "确认覆盖" → "初步表明 250% 阈值覆盖 203-209% 区间"
  - "Test 24 不再 flaky" → "Test 24 首轮未触发 flakiness"
  - 在"关键意义"段补一句："单轮验证不足以确认 flakiness 消除（修复前 #143/#144 也曾 success），需 10+ 轮长期监控最终确认"
- **为什么这么修**：诚实区分"单轮观察"与"统计确认"。这与 Worker 待办里的"长期监控"措辞对齐，也与 v6.5.0 反复强调的"单次数据不可靠"（v6.3.0 教训）方法论一致。修复方向本身没问题（250% 合理），但措辞不应跑在数据前面。

## 六、总体评价

### 优点
1. **修复方向正确**：250% 阈值基于实测数据（203-209%），给 ~20% 余量，保留 >250% 仍 FAIL 的断言价值，与 v6.3.0 修复思路一致。
2. **验证方法严谨**：未止步于 conclusion=success，而是进一步查 annotations 确认"无 Test 24 失败 annotation"，区分了"job success"与"Test 24 实际执行通过"。
3. **代码修改干净**：1 行阈值 + 全链路同步（PASS/FAIL/诊断/注释），无遗漏，注释质量高。
4. **文档同步全面**：5 个文档同步更新，表格设计（修复前/后列）清晰。

### 成长点
1. **数据完整性意识**：#144 遗漏暴露了"数据收集聚焦失败轮次、忽略 success 轮次"的倾向。后续多轮分析应确保**全量轮次**纳入表格，包括 success 轮（它们对判断 flakiness 频率同样重要）。
2. **结论措辞与证据匹配**：单轮验证用"确认/通过"，多轮监控用"待确认" — 正文措辞不应比待办更强。这是"诚实记录"准则的延伸：不仅踩坑要诚实，结论也要与证据强度匹配。

### 团队可学习经验
- **flakiness 修复的验证标准**：间歇性故障（flakiness）的修复验证不能靠单轮 — 因为修复前本身就有 success 轮。验证应基于"足够多轮次后失败率显著下降"，而非"修复后首轮 success"。这是 flakiness 类问题与普通 bug 修复的本质区别。
