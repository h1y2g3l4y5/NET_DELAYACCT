### 议题 1: tc netem 在 loopback 上的可用性（问题 2.3.2）

**Worker 意见**:
> tc netem 在 loopback 上的行为与真实网卡不同：
> - loopback 是虚拟设备，无真实队列延迟，netem 的丢包发生在入队前
> - 10% loss 在 loopback 上是否真的能触发 TCP 重传？需要实际验证
> - 备选方案：iptables -I INPUT -p tcp --dport <port> -j DROP 更可靠，但需要确认 QEMU 环境有 iptables

**Reviewer 回应**: **部分同意，调整方案**。

经核实 [ci/qemu/kernel-qemu.config](file:///home/lai/Code/NET_DELAYACCT/ci/qemu/kernel-qemu.config) 当前只启用了 `CONFIG_NETFILTER` 和 `CONFIG_NETFILTER_ADVANCED`，**未显式启用 `CONFIG_NET_SCH_NETEM`**，也未启用 `CONFIG_IP_NF_IPTABLES`（iptables 依赖）。

我的看法：
1. **netem 确实存在不确定性**：Worker 的担心合理。netem 作为 classless qdisc 理论上可挂到 loopback，但 loopback 的 `lo_setup()` 默认挂载的是 `noqueue`，netem 替换后的丢包行为需要实测。在 QEMU TCG 慢速环境下，netem 的 random loss 伪随机数生成器行为也可能与预期有偏差。
2. **iptables 方案更直接但同样缺配置**：`CONFIG_NETFILTER` 已启用，但 `iptables -j DROP` 依赖 `CONFIG_IP_NF_FILTER` 和 `CONFIG_NETFILTER_XTABLES`，当前均未显式启用。两条路都需要先补内核配置。
3. **推荐折中方案：双轨备选 + 实测兜底**：
   - **主方案**：在 [ci/qemu/kernel-qemu.config](file:///home/lai/Code/NET_DELAYACCT/ci/qemu/kernel-qemu.config) 同时启用 `CONFIG_NET_SCH_NETEM`、`CONFIG_NETFILTER_XTABLES`、`CONFIG_IP_NF_FILTER`。
   - **Test 23 S7 实现**：先尝试 `tc netem loss 10%`，用 `tc -s qdisc show dev lo` 确认丢包计数非零；若 netem 失效（`tc` 返回非零或丢包计数为 0），自动降级到 `iptables -I INPUT -p tcp --dport <port> -m statistic --mode random --probability 0.1 -j DROP`。
   - **断言层面**：S7 的关键断言是 ftrace 观测到 `__tcp_retransmit_skb` 调用次数 > 0，而非依赖丢包工具本身是否生效。如果 `__tcp_retransmit_skb` 计数为 0，无论用 netem 还是 iptables 都判 FAIL，并输出诊断（`tc -s` 或 `iptables -L -n -v` 统计）。
4. **严重度调整**：将 2.3.2 严重度从"高"下调为"中"。理由：`__tcp_retransmit_skb` 的打点在 [tx-instrumentation.patch#L98](file:///home/lai/Code/NET_DELAYACCT/kernel-patches/tx-instrumentation.patch#L98) 是独立的 `pskb_copy` 块，逻辑简单（`nskb` 分配后立即打点，无分支误判风险），打点位置错误的概率低于 splice/zerocopy 路径。即使 S7 无法稳定触发，也不阻塞 v6.1.0 闭环——可作为"已知限制"记录，待真实网卡环境或 netem 验证后补强。

调整后的建议：
- 启用三个内核配置项作为 P0
- S7 实现采用 netem → iptables 降级策略
- 若两者均不可用，S7 改为 `_skip` 而非 `_fail`，避免环境限制导致 CI 红灯
