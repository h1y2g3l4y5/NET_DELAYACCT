### 架构决策

#### 决策1：CI perf-test 用 `--strict=warn` 模式（非 `--strict=fail`）

- **背景**：共享 runner 噪声大于本地专用机，INVALID（噪声主导）和 FAIL（指标超阈）可能频繁触发
- **备选方案**：A（`--strict=fail` FAIL/INVALID 阻断）/ B（`--strict=warn` FAIL/INVALID 告警不阻断）/ C（无 strict 模式，统一告警）
- **最终选择**：B
- **理由**：共享 runner 噪声不可控，FAIL=fail 会导致 CI 频繁红；FAIL→warn 设计让 perf-test 作为趋势监控信号（signal not gate），不阻断功能合并；NO-DATA 和 INVALID>50% 仍 exit 2（数据不可信，真实问题）

#### 决策2：FAIL→warn 模式下 FAIL → exit 0（commit c720aa6）

- **背景**：run #139 阈值修复后 perf-test job 仍 exit 1（推测 cpu_util +7.9% 接近 10% 阈值被噪声推过）
- **备选方案**：A（保持 FAIL → exit 1，依赖 continue-on-error）/ B（FAIL → exit 0 告警，仅 NO-DATA/INVALID>50% 阻断）
- **最终选择**：B
- **理由**：continue-on-error 会让 perf-test job 永远是黄/红色，失去趋势监控价值；FAIL→exit 0 让 job 显示绿色，FAIL 详情仍在 Verdict 区 + Step Summary 输出供分析；NO-DATA/INVALID>50% 仍 exit 2，覆盖真实问题

#### 决策3：verdict 优先级链 FAIL > INVALID > NO-DATA > PASS

- **背景**：v6.4.0 verdict 三态（PASS/FAIL/INVALID）在 CI 接入后暴露"全 SKIP 假 PASS"隐患
- **备选方案**：A（保持 v6.4.0 三态，依赖 set -e 传播全 SKIP 失败）/ B（新增 NO-DATA 第四态 + verdict_pass 计数）
- **最终选择**：B
- **理由**：QEMU 启动但无 PERF: 数据（内核 panic / guest init 失败）时 result_file 存在通过文件检查，但所有 metric 数据为空 → 全 SKIP → 假 ALL PASSED。这是 v6.4.0 假 PASS（噪声数据）的同类隐患（无数据），CI 接入后假 PASS 危害放大。`verdict_pass` 计数器是正确解法：`pass+fail+invalid=0` 即 NO-DATA → exit 2

#### 决策4：latency 阈值 10μs 绝对 → 10% 相对（TASK-54）

- **背景**：CI KVM run #137 实测 connect() 延迟 ~3800μs，10μs 绝对阈值 = 0.26% of total，远低于噪声；+115μs (3.1%) 在噪声范围内
- **备选方案**：A（保持 10μs 绝对）/ B（改为 10% 相对）/ C（改为 100μs 绝对）
- **最终选择**：B
- **理由**：与 throughput/cpu 指标一致使用相对百分比阈值；10% 相对阈值对 3800μs 基线 = 380μs 余量，覆盖正常波动；KVM 实测 +3.1% PASS

#### 决策5：sock 阈值 80 → 192 bytes（TASK-54）

- **背景**：CI KVM run #137 实测 sock objsize delta +128 bytes > 80 阈值。`/proc/slabinfo` 第 4 列报 `s->size`（含 SLAB_HWCACHE_ALIGN 64 字节对齐填充），非 `s->object_size`（原始 struct 72B）
- **备选方案**：A（保持 80）/ B（改为 192 = 128 + 50% 余量）/ C（用 sysfs object_size 精确测量）
- **最终选择**：B
- **理由**：sysfs `object_size` 需 `CONFIG_SLUB_DEBUG_ON=y` 才有值，不可用；slabinfo 是 guest 内 root 可读的可靠数据源；pahole 确认原始 struct 72B，56B 为对齐填充，192 阈值覆盖对齐后值 + 余量

#### 决策6：Test 24 ratio 阈值 200% → 250%（TASK-55）

- **背景**：5 轮 CI KVM 数据分析发现 Test 24 在共享 runner 上 flaky —— 2/4 轮失败（ratio=203-209% > 200% 阈值）
- **备选方案**：A（放宽 ratio 200%→250%）/ B（ratio 改自适应阈值）/ C（QEMU test 加 continue-on-error）/ D（flaky retries）
- **最终选择**：A
- **理由**：最小变更（1 行）；250% 给 ~20% 余量覆盖共享 runner 噪声；> 250% 仍 FAIL 捕获真正多打点 bug；方案 C 掩盖真实回归，方案 D 增加 CI 时间不解决根因
- **验证**：run #145 (commit bf58488) 6/6 jobs 全绿，QEMU runtime test success（353s），无 Test 24 失败 annotation → 250% 阈值覆盖 203-209% 噪声区间，flakiness 修复确认

### 关键议题复盘

#### 议题1（规划阶段）：KVM 环境数据补齐方案 — 共识-调整顺序

- **问题**：本地无 /dev/kvm，无法本地 KVM 多轮收集

- **最终方案**：执行顺序 50→51→52→48(CI)→49，初始用 TCG 阈值，CI 中逐步校准
- **教训**：本地无 KVM 时，CI 是唯一可行路径，需先接入 CI 再补数据

#### 议题2（规划阶段）：CI 接入实施方案 — 接受

- **问题**：CI 需双内核构建（matrix）+ perf-test job + verdict 处理策略
- **讨论**：Worker 补充 qemu-test artifact 下载需同步改 bzImage-on
- **最终方案**：matrix [on, off] + 独立 perf-test job + `--strict=warn` + `continue-on-error`
- **教训**：matrix 化后下游 job 的 artifact 依赖需同步修改，主动排查下游影响

#### 议题3（实现复审）：CI perf-test job timeout 与 QEMU timeout 不匹配 — 接受

- **问题**：CI job `timeout-minutes: 10` 与 perf-test.sh 内部 QEMU_TIMEOUT_KVM=300×2=600s 恰好相等，无余量；TCG 模式 1200s 必定 timeout
- **修复**：CI 步骤中通过环境变量缩短 QEMU timeout：`QEMU_TIMEOUT_KVM: 240, QEMU_TIMEOUT_TCG: 360`，`timeout-minutes: 15`
- **教训**：CI job timeout 必须大于内部所有 timeout 之和 + 余量（apt install + checkout + boot 等）

#### 议题4（实现复审）：compare_and_report return 1 未设 PERF_EXIT — 接受

- **问题**：`compare_and_report` missing-files 分支 `return 1` 未设 PERF_EXIT，依赖 set -e 传播；维护者修改 pipeline 结构时极易引入假 PASS
- **修复**：显式设置 `PERF_EXIT=1` + 主流程 `compare_and_report || true` 防止 set -e 绕过 PERF_EXIT_FILE 写入
- **教训**：verdict 类逻辑不可依赖"默认成功"或"隐式行为"，必须显式追踪所有状态；PERF_EXIT 必须是 exit code 的唯一来源

#### 议题5（收尾，补遗发现）：Test 24 ratio 阈值在共享 runner 上偏紧 — 接受

- **问题**：5 轮 CI KVM 数据分析发现 Test 24 ratio=203-209% 超 200% 阈值（2/4 轮失败），是 workflow failure 主因
- **修复**：ratio 上限 200% → 250%（1 行代码）
- **教训**：CI 多轮数据分析时应同时审查性能测试和功能测试的阈值稳定性，不能因任务边界忽略同源问题

### 系统性教训

- **教训1：CI 共享 runner 噪声适配是设计哲学问题**。v6.5.0 经历三轮设计迭代：①阈值修复（80→192, 10μs→10%）→ ②FAIL→warn 设计（FAIL→exit 0）→ ③Test 24 ratio 放宽（200%→250%）。核心教训是共享 runner 上的性能/计数类指标不能用绝对阈值硬门禁，必须用"signal not gate"哲学：趋势监控 + 噪声容忍 + 真实问题（NO-DATA/数据不可信）仍阻断。
- **教训2：verdict 类逻辑必须显式追踪所有状态**。v6.4.0 假 PASS（噪声 INVALID 误判 PASS）和 v6.5.0 假 PASS（全 SKIP 无数据）是同类隐患 —— "else=成功"兜底是假绿风险。verdict 优先级链 FAIL > INVALID > NO-DATA > PASS 必须显式追踪 pass/fail/invalid/skip 四种状态。
- **教训3：CI 多轮数据分析需同时审查性能和功能阈值**。TASK-49 初版仅评估 perf-test 阈值，未触及 Test 24 功能测试阈值。Test 24 ratio 阈值过紧同样是"共享 runner 噪声"导致的阈值问题，但因任务边界被忽略。后续 CI 多轮分析应统一审查所有阈值。
- **教训4：GitHub API 认证边界需区分**。`logs_url` 需 admin；`annotations_url` 和 `check-runs conclusion` 公开只读。诊断 CI 失败应优先尝试 annotations API，无需 admin token 即可获取失败摘要（exit code + Test 24 失败信息）。
- **教训5：#ifdef 守卫必须字段+调用同步**。struct 字段被 `#ifdef CONFIG_X` 守卫时，任何引用该字段的调用（即使通过空桩函数）也必须加同样守卫。CI 此前只建 ON 内核未暴露此问题，matrix 化构建 OFF 内核后立即暴露 —— 双内核 CI 是发现配置依赖 bug 的必要条件。

## 九、版本意义

v6.5.0 是 NET_DELAYACCT 项目从"功能正确性验证"走向"性能可观测性落地"的关键版本：

1. **CI 接入兑现**：实现了 v6.4.0 承诺的"阈值稳定后接入 CI"，perf-test job 正式成为 CI pipeline 一部分
2. **"signal not gate" 哲学确立**：FAIL→warn 设计确立了性能测试在 CI 中的角色 —— 趋势监控信号而非功能门禁，为后续 strict=fail 严格回归留出空间
3. **多轮数据驱动校准**：5 轮 CI KVM workflow verdict 驱动阈值校准（latency/sock 阈值修复 + Test 24 ratio 放宽），体现了 v6.3.0 "单次数据不可靠" 教训的实践
4. **结构性 bug 修复**：OFF 内核构建 bug（#ifdef 守卫）暴露了 v6.4.0 单内核 CI 的盲区，matrix 化双内核构建是发现配置依赖 bug 的必要条件
5. **方法论沉淀**：verdict 优先级链 FAIL > INVALID > NO-DATA > PASS、GitHub API 认证边界区分、CI 多轮数据统一审查性能/功能阈值等方法论将指导 v6.6.0 及后续版本
